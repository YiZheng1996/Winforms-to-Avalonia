## 5. F1：试验结果和报表正确性

### 5.1 固定判定规则

- 序列快照是本次必须执行项点集合，禁止用当前型号配置代替。
- 正常结束要求每个预期项点恰有一个有效终态结果，不允许额外项点、重复项点、缺项或 Pending/Running。
- 全部 Passed 才进入 Completed；有 Failed 则进入 Failed；Aborted 不得算通过。第一版不支持可选项点，Skipped 阻止正常完成并显示原因。
- 中止走独立 Abort 用例，允许尚有未执行项；已经保存的结果不删除。
- 第一版同一记录同一项点不支持重测：重复请求不得再运行执行器；需要重测时创建新记录。后续如需重测，单独设计尝试次数及有效结果规则。
- 启动和执行均核对记录模式、当前模式和 runtime.Mode/IsSimulation 一致；模拟结果必须标注仿真。

### 5.2 编码任务

- [ ] `CompleteCoreAsync` 校验序列集合、终态和数量，明确错误信息；结束状态更新采用 Running 条件更新并检查受影响行数。
- [ ] 执行前持久化项点 Running 占位，执行后更新同一行；异常/取消保留 Failed/Aborted 结果及原因，不留下无记录的执行。
- [ ] 数据库对 `(record_id, test_item_point_id)` 建唯一约束；存量重复不得任意删除或挑选，应先归档并给出人工处置清单，未处置前阻止该迁移。
- [ ] 新运行中增加请求去重；数据库事务不能跨越设备 IO，先提交占位，再执行，再短事务收尾。
- [ ] 报告允许 Completed 和 Failed；Aborted 仅输出明确标注的中止记录报告，Running 禁止生成最终报告。
- [ ] 报告按序列及唯一结果取数；损坏或缺失快照不得默默生成“正常”报告。
- [ ] 首页移除硬编码压力值。没有采样源时显示“未配置/无有效数据”；仿真值显示仿真标识，禁止用零冒充正常测量。

验收案例：3 项仅做 1 项不能完成；3 项全通过才能通过；失败、中止、跳过不误判；重复点击只执行一次；不合格报告可生成且与记录一致。

## 6. F2：统一运行协调与安全边界

### 6.1 运行协调器（拟新增 `src/XXX.TestBench.Core/Application/TestRunCoordinator.cs`）

- [ ] 第一版每个应用实例最多一个活动试验；部署为单实例，防止两进程同时控制同一设备。数据库活动状态约束作为补充，不以页面按钮禁用代替互斥。
- [ ] 协调器持有活动 RecordId、取消源、执行任务及当前阶段，页面只观察状态和发送命令；切换页面不会遗失执行。
- [ ] 启动、完成、中止、配置应用和模式切换共用操作门；复用多设备子计划的操作门，禁止重复锁或持锁等待 UI 确认。
- [ ] 启动失败的持久化记录必须收尾；重复启动返回明确拒绝，不能覆盖页面记录编号。
- [ ] 退出请求先停止业务；在配置的期限内等待收尾、停止采集并释放运行时、数据库和日志。失败保留诊断，不能吞异常后显示安全完成。
- [ ] 重启发现遗留 Running 记录时标为异常中止并记录原因，不自动续跑或重放设备命令。恢复只恢复记录可见性，不等于恢复物理动作。
- [ ] 软件停止与设备安全动作分离：执行器提供受控停止策略；未知设备状态显示“停止结果不确定”。不得把软件取消当作硬件急停证明。

### 6.2 权限和写入

- [ ] 新增统一操作身份解析边界，每次启动、写入、校准、配置变更、用户管理和报告操作验证会话、用户启用状态、强制改密及最新权限；不可只校验缓存 UserContext。
- [ ] 停用用户、重置密码、变更角色/权限后撤销受影响会话，并刷新页面登录状态。保持当前密码策略，不擅自提高密码复杂度。
- [ ] 活动试验中会话失效时，禁止新的人工控制和新项点启动，通知协调器受控停止；系统停止清理不依赖已经失效的用户权限，审计保留原操作者和系统原因。
- [ ] 写入场景明确分为试验控制、空闲维护、校准；空闲维护不再要求先创建一个试验记录。每种场景定义允许状态和权限，试验中默认拒绝无关维护写入。
- [ ] 写前验证目标数据质量、新鲜度、类型、范围和必需联锁；联锁策略缺失时拒绝受保护动作。高风险确认绑定一次目标和值，成功/失败后清除，不能用长期勾选替代每次确认。
- [ ] 请求、拒绝、已发出、确认成功、失败、结果不确定分别审计；写超时禁止自动重发。真实回读及连接代次按设备子计划实现。
- [ ] 审计故障规则：发出高风险写前无法保存意图则拒绝；设备已执行后审计失败不能声称未执行，应报审计故障并阻止后续危险动作。

验收：并发启动只成功一次；关闭/取消/异常后无悬挂运行；会话过期或停用后操作失败；空闲授权校准可以进入专用流程；写失败仍有可追溯状态。

## 9. F5：自动执行、报警、趋势与校准

### 9.1 自动执行

- [ ] 协调器按序列快照顺序执行，第一版失败即停止后续项点并结束为 Failed；未执行项在失败详情中明确展示，不伪装成通过。

### 9.2 报警

- [ ] 拟新增 AlarmDefinition、AlarmEvent、AlarmService 和仓储；规则包含信号、上下限/布尔条件、等级、延时、回差、启用状态。

- [ ] 报警判定使用采集快照，界面关闭不影响报警；报警展示与设备硬联锁区分，关键联锁仍须在控制边界校验。
- [ ] 提供活动报警和历史筛选页；确认操作需要明确权限并审计。

### 9.3 曲线与采样存储

- [ ] 拟新增采样存储接口和服务；首版只保存配置选中的点位，不默认保存所有数据。

- [ ] UI 环形缓冲和降采样；历史查询按时间范围和最大点数限制，避免把整库数据载入内存。
- [ ] 实时/历史曲线显示单位、时间轴和质量中断；坏质量期间不得连线假装连续测量。提供区间导出。
- [ ] 图表库选型先验证完整许可证与目标平台，形成记录后接入可替换展示适配层。

### 9.4 校准

- [ ] 首版实现明确的两点线性校准：输入标准值、读取稳定原始值、计算并校验系数、预览、确认生效。
- [ ] 记录设备/点位身份、标准值、原始值、前后系数、操作员、时间、原因和有效期；校准版本进入试验快照。
- [ ] 拒绝原始点相同、坏质量、越界或试验中生效；校准失败保持旧系数。区分软件换算系数和仪器内部寄存器校准，后者需独立驱动支持。

验收：自动试验超时可收尾；报警抖动不重复刷屏；确认与恢复互不替代；长时间采样内存有上限；校准失败不改变生效系数。

## 10. F6：报表与界面统一

- [ ] 固定模板输入契约，模板路径按配置解析为绝对路径；指定模板缺失/损坏时明确失败，禁止静默换版式。无模板模式仅允许显式选择内置标准模板。
- [ ] 清理模板旧数据区，避免本次项点较少时残留旧行；并发生成使用唯一输出名和临时文件原子落盘，防止同秒覆盖。
- [ ] 保存模板版本/哈希、报告生成版本及输出哈希，报告与记录关联；失败允许重试，不更改原试验结论。
- [ ] 批次、工位、备注等产品标识在记录详情和适用报告中完整显示。
- [ ] 引入报告预览/导出/打印接口；按选定开源免费方案分别实现。不能用“能生成 XLSX”代替预览、PDF或打印验收。
- [ ] 显示层统一状态、质量和模式中文映射；存储保持稳定内部代码。所有页面和报告采用明确时区，存储继续 UTC，不直接格式化 UTC 冒充本地时间。
- [ ] 异步选择查询加入取消或请求版本检查，旧查询返回不能覆盖新选中记录；统一异常提示、忙状态和命令可用性。
- [ ] 中文字体、长标题、行选择、滚动和弹窗操作在目标分辨率/DPI 检查。

验收：无残留旧报告行；同秒报告不覆盖；改名不改变旧报告；不同选择不串详情；长报告分页和实际打印单独留证据。

## 11. F7：跨平台与运维

- [ ] 拟新增应用路径服务，区分只读程序资源、可写配置、业务数据、日志、报告与备份；支持明确路径覆盖。应用正式运行目录按部署方案确定，不使用开发临时目录。
- [ ] 从旧程序 data 目录迁移时先识别和备份，目标已有数据不能覆盖，完成校验后记录迁移结果；禁止无提示创建空库造成“历史数据消失”。
- [ ] 初始化异步化并显示阶段/错误；日志创建失败也有可见诊断。将完整性重检查安排为明确维护操作，评估每次启动全库检查的耗时。
- [ ] 日志按日期/大小轮转，配置保留期和磁盘上限；清理仅限所属目录和可识别文件，不递归删除业务数据。
- [ ] 诊断包包含版本、配置摘要、运行状态和相关日志，排除密码哈希、会话令牌等敏感字段。
- [ ] 分开输出 Windows、Linux 各架构发布包；维护系统版本、CPU、运行时、原生依赖、字体和驱动支持矩阵。未验证组合标记待验证。
- [ ] 信创现场验证普通用户权限、串口设备权限、中文输入、触控、缩放、文件选择、网络、报告及打印。
- [ ] 更新流程包含停止、备份、安装、迁移、冒烟和失败恢复；不增加无需求的在线自动更新。

验收：程序目录只读时可正常使用；切换启动工作目录不影响配置/模板定位；跨天日志轮转；退出释放；目标系统离线安装可复现。

## 13. 验证执行与性能基线

1. 先核对 `dotnet --info`。支持 `--artifacts-path` 时统一指向 `D:\Codex相关\框架完善\artifacts`；否则配置按项目隔离的中间和输出目录，不共用单个 obj。
2. 配置 TEMP/TMP、必要时 NUGET_PACKAGES 到任务目录；已有可读缓存可复用，不删除用户缓存。测试结果输出到 `D:\Codex相关\框架完善\test-results`。
3. 构建后按 Core → Integration → App → Headless 顺序执行。只终止本次产生的挂起进程；锁库、超时、跳过不得算通过。
4. 记录源码版本及未提交差异范围、命令、环境、退出码、通过/失败/跳过数量。旧二进制测试不能充当当前源码验证。
5. 工程性能初始负载：十万记录分页、500 个仿真点按 500ms 更新、20 个选定点按 100ms 存储、持续 2 小时。记录 CPU、内存、采样延迟、写入队列和丢样数；这是工程基线，不是承诺所有现场负载。
6. 队列和 UI 缓冲必须有配置上限，压力测试后不持续增长；列表只读取请求页。响应时间预算在 F0 记录目标测试机后确定，不事后放宽阈值掩盖失败。
7. 目标硬件执行更长时间及拔插恢复验证，由现场负载和验收要求确定；软件压力测试不替代 PLC/UOS/现场验收。
